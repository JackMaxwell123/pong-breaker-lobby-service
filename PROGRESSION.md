# Progression extension v1

This extends `PONG_BREAKER_WEBRTC_1`. Direct WebRTC gameplay and the existing relay remain unchanged. Guest/private play continues when progression is unavailable. `round_complete` never credits currency or affects rating.

## Readiness and storage

`welcome` includes `progression_version:1` and `capabilities:{economy,ranked,match_rewards,ads,purchases,progression_version:1}`. A missing extension means an older server; do not send it credentials. Capability values are server configuration, never client switches.

Production: configure `PB_DATABASE_URL` to a PostgreSQL connection string with TLS (`sslmode=verify-full` preferred with the provider CA; at least `require`). Configure `PB_DURABLE_STORAGE=1` only after checking the database retention/backup policy. Install `requirements-progression.txt`. No database credentials belong in the Android build. No provider is provisioned by this code. A free database provider's quotas, suspension and retention rules must be checked before release.

Development SQLite: `PB_SQLITE_PATH` creates the schema but does not advertise the economy by default. `PB_SQLITE_PERSISTENT_VOLUME=1` explicitly attests an actual persistent volume and enables it; do not set this on ephemeral Render free storage. Render without this declaration refuses a SQLite launch. Existing `render.yaml` intentionally leaves the economy/ranked/purchase/ad gates closed. Losing a local database must never silently create an apparently restored account.

The database stores hashed, 256-bit bearer player keys. The original key is returned only once. Save it immediately and protect it. A key is a portable account recovery secret, not a public player name. There is no email/password account system, password reset, key export UI or administrative recovery promise. Invalid saved keys fail without creating a replacement account. The server never logs keys, receipts or database URLs. Clients must scope saved keys to an approved TLS service origin and never send them to arbitrary custom servers.

## Account, shop and reward messages

Every request retains the existing unique `request_id` envelope. Mutation `operation_id` is a second stable retry key, 8–80 ASCII letters/digits/underscore/hyphen. Reuse it for retries of the SAME operation on a new request/connection. Changing its payload fails. Currency and ownership changes share one transaction. Rebuying an owned cosmetic never debits twice. Free classic styles and ball_1/paddle_1/brick_1 are owned from creation, alongside 150 welcome coins.

| Request | Fields | Response |
|---|---|---|
| `account_auth` | optional `token` (omit only for a new account) | `account` with `profile`, `catalog`, `capabilities`; `token` only for a newly created account |
| `account_delete` | `confirmation:"DELETE"`, `operation_id` | `account_deleted`; removes collection, wallet, key access and active sessions |
| `profile_get`, `reward_status` | none | `profile` with `profile`, `capabilities` |
| `catalog_get` | none | `catalog` with item array |
| `shop_buy` | `item_id`, `operation_id` | `purchase` with `result:{item_id,spent,already_owned}`, current `profile` |
| `cosmetic_equip` | `slot`, `item_id`, `operation_id` | `equipped` with `result`, current `profile`; refreshes lobby cosmetic display |
| `reward_prepare` | `operation_id` | `reward_prepared` with `custom_data`, `ssv_user_id`, `expires_at`, `coins` |
| `reward_claim` | `operation_id` | `reward_granted` with `result`, current `profile`; verified supporters only |
| `purchase_submit` | `product_id`, `purchase_token`, `operation_id` | `purchase` with `result`, current `profile` |

Profile shape: `account_id`, `billing_account_id` (SHA256 of account ID, for Google billing binding), integer `coins`, string array `owned`, `equipped:{ball,paddle,brick,theme}`, boolean `supporter`, `ranked:{rating,games,wins,provisional,placements_remaining,division}`, `reward:{coins:50,cooldown_seconds:14400,available_at,server_time}`, and `recent_receipts` (the latest ten completed/rejected settlements for reconnect recovery). Reward timestamps are Unix UTC seconds. Device clock changes cannot advance rewards. A new `reward_prepare` operation is required after its ten-minute challenge expires.

An idle, already authenticated connection may restore a different valid token; its previous profile is replaced only after token validation. Account deletion requires explicit DELETE confirmation while idle. It erases ownership, wallet, custom equipment, cooldown and local-operation history, makes the old key unusable, and clears other active sessions. Minimal pseudonymous purchase/ad transaction identifiers and match-fraud records remain to prevent replaying already consumed receipts. There is no name/email stored. These retention facts must be visible in the release privacy/deletion notice; deleting an account is not a store refund. Existing spent purchase tokens cannot be redeemed into a new account afterward.

IDs: `ball_1..8`, `paddle_1..8`, `brick_1..6`, `theme_conservatory`, `theme_observatory`, `theme_cloudline`, `theme_arcade`; classic IDs are `ball_classic`, `paddle_classic`, `brick_classic`, `theme_classic`. Wide paddles are paired art, never a separate purchase. Cosmetic equip requests require ownership and correct slot. Shared cosmetic changes are held until the current match ends.

No network command grants coins or entitlements by itself. `purchase_submit` verifies the account-bound Google purchase, commits a durable idempotent entitlement, then consumes/acknowledges the product. If finalization fails, `result.finalized=false`; retry the SAME token so acknowledgement can finish without duplicating the grant. Only products `coins_500`, `coins_1500`, `supporter_coffee` exist. An SDK success callback is not a grant. AdMob calls `/rewards/admob?<original signed query>`; only a valid signed, account-bound, unexpired challenge callback can award the same 50 coins/4-hour cooldown. There is no forced ad. Supporters claim the identical reward without an ad and do not get a shorter cooldown. No reward is auto-collected while offline.

Paid purchases additionally require `PLAY_RECEIPT_ENCRYPTION_KEY` (a separately managed Fernet key) and a successful authenticated Voided Purchases reconciliation. Pending raw tokens are stored only as authenticated ciphertext until Google consumption/acknowledgement succeeds, then erased. Never commit this key or log a token. Keep the old encryption key available until its pending queue is cleared before rotating it. The worker runs at startup and every thirty minutes; failed finalization is retried from durable storage. The refund feed uses a 29-day overlap with idempotent token-hash revocation. A stored reconciliation checkpoint older than that window blocks new paid purchases pending operator review. This job cannot recover refunds Google no longer exposes after a long outage.

Refund policy: unspent paid coins are tracked separately behind the single displayed balance; cosmetic purchases spend those paid coins first. A verified refund removes only the remaining coins from that purchase, preserving earned coins and all already-owned cosmetics. If some refunded paid coins were spent, `profile.store_review=true` blocks further real-money purchases pending support review, while play, earned rewards, and the coin cosmetic shop remain usable. A verified supporter refund removes ad-skip entitlement. No negative balance, automatic cosmetic seizure, ranked ban or fabricated debt is imposed. This policy must be explained before purchase. Account deletion keeps the minimal token-hash ledger necessary to prevent replay and process later refunds.

## Matchmaking and independent replay

`quick_match` accepts optional `mode:"casual"|"ranked"` (default casual) and `game_protocol`. Queues never mix gameplay protocols or ranked/casual modes. Ranked requires `game_protocol:"PONG_BREAKER_1_4"`, an authenticated durable account and a configured headless verifier. Legacy guests without a gameplay protocol remain eligible for unranked guest queues only. Initial skill window ±150 rating expands 75 per 15 seconds to ±600; it is rechecked while waiting. A player cannot match their own account. Private rooms and browsable lobbies never pay rewards. Automatic public matchmaking is the only eligible entry path. Ordinary rematches still require independent replay and receive repeated-opponent protection.

Room snapshots include `mode`, `matchmade` and each player's server-owned `cosmetics`/`ranked` fields. `start` includes server-generated `seed`, `match_id` (same as `round_id`), `mode`, `reward_eligible`, and `replay:{version:1,fps:60,max_frames:54000,chunk_frames:120,simulation_sha256}`. Pin compatible client simulation builds to that hash. An older client can play casual but cannot fabricate rewards.

Both clients upload the same observed, applied input stream, not a winner or score. Frame order is **set both aim values → `sim.step(1/60, targets)` → release flagged held balls**. Begin after the match countdown. Apply the quantized inputs to actual play, not only to the log. Every frame is `[x0,x1,aim0,aim1,release0,release1]`: six integers, x is world x multiplied by 1000 (6000..354000), aim multiplied by 1000 (-1000..1000), release flags 0 or 1. Target clamp remains in the shipped simulation. Include the frame which finishes the game and no frames after it.

`replay_chunk {match_id,offset,frames}` accepts 1..120 frames at a time, exact contiguous offset from zero. Response `replay_ack {match_id,offset}` gives the next expected offset. Stream at ≤10 chunks/second and wait for acknowledgements; normal control-message rate limits apply. Retry/reconnect support is intentionally conservative: do not automatically replay already acknowledged chunks under a new offset. Requests that overlap or skip input are rejected.

For SHA256, encode each frame as a compact ASCII JSON array with no spaces followed by one LF byte, concatenate in order, and hash these bytes. `replay_seal {match_id,sha256,frames:<count>}` seals that player's upload. Response `replay_pending` means waiting for the other player or verifier, never that coins were granted. Different independent seals reject the match without a winner claim. A local peer should also validate that the host's log agrees with its own input history; peer agreement alone is not an anti-cheat guarantee.

Server config `PB_GODOT_BINARY` points to a real matching Godot binary. `PB_REPLAY_SIMULATION` points to the exact release simulation.gd (default sibling game scripts). The server-only project loads this trusted source and the JSON input file, never client GDScript/native objects. Two verification processes maximum; hard 45-second process timeout, 15-minute/54000-frame match cap, eight active eligible uploads, bounded 16-KiB messages. Minimum rewarded duration is 30 seconds and elapsed wall time must agree (5-second tolerance). Replays expire after 20 minutes; missing/disputed/disconnected matches pay no fabricated reward or arbitrary ranked loss. There is no daily ordinary-match earnings cap.

The release verifier is pinned to Godot **4.7.2 stable**, checked at startup. `install_verifier.py` fetches the official Linux x86_64 release archive and checks SHA512 `9aa00f7a605200940bce3027a567b782f49bd8e940dd06ae9e987bd65aee1b1467edd56ed84fcdcbdd44354bf613bdbb4e5d2913e925850368e150c59ed54c65` before installing. The checksum comes from the [official 4.7.2 release checksum file](https://github.com/godotengine/godot-builds/releases/download/4.7.2-stable/SHA512-SUMS.txt). The container supplies Linux runtime libraries; a native Python deployment must supply them independently. The server-only package must contain `verifier/simulation.gd` copied byte-for-byte from this release. Resync and compare hashes whenever simulation changes.

## No-cost staging setup, not a paid deployment

Use the existing Render free web service with a **separate durable PostgreSQL database**, not Render's expiring free PostgreSQL trial. Render documents its free web filesystem as ephemeral and its free PostgreSQL database lifetime as thirty days: [Render free limits](https://render.com/docs/free). An eligible external free option is Neon; its [October 2, 2026 free-plan announcement](https://neon.com/blog/neon-free-plan-1-gb-per-project) lists 1 GB storage per project and 100 CU-hours monthly. These are quotas, not an unlimited-production promise or a backup substitute. The new database account and terms still need the owner's approval; this package does not create them or add a payment method.

1. Create a Free Neon project in a region near the Render service, using a dedicated database role; leave paid upgrades and payment methods disabled. Save its TLS PostgreSQL connection string as a Render secret `PB_DATABASE_URL`, never in the app or repository.
2. Prepare and inspect the server-only repository with these files and the exact `verifier/simulation.gd`. The current Blueprint uses Docker so Linux runtime dependencies and the checksum-pinned engine are reproducible. Keep `plan: free`, automatic deployments off, and health path `/healthz`. An existing native-Python service may require an owner-approved new Docker service; do not silently replace the live endpoint.
3. Establish durable backup/export and restore procedures within free quotas. Only then set `PB_DURABLE_STORAGE=1`. Start with store/ad flags absent. Verify `welcome.capabilities.economy=true` and `ranked=true`, then run owned test clients. Never send actual user keys to a test endpoint.
4. Exercise the PostgreSQL adapter against an explicitly supplied staging URL: install `requirements-progression.txt`, set `PB_TEST_POSTGRES_URL`, and run `python run_tests.py`. It creates/removes only a random `pong_test_*` schema. No PostgreSQL binary or provider was available in this local validation; this test remains opt-in and must pass before production accounts are enabled.
5. Keep paid purchases and rewarded ads disabled until Google Play/AdMob configuration, consent/audience review, encrypted finalization retries, refund reconciliation and real-device license-test purchases are verified. The code has no live account credentials and charges nobody.

Idle guest-only servers do not poll the database every minute: expired matches are revisited when players return, allowing serverless PostgreSQL to scale to zero. If commerce is enabled, its thirty-minute reconciliation wakes the database periodically and consumes some free compute allowance; include that in measured capacity. A wallet outage disables rewards and ranked starts, while a casual game can continue explicitly without rewards.

## Encrypted operator backup and restore drill

`backup_restore.py` provides a bounded logical export of every ledger table, with a repeatable read snapshot on PostgreSQL. It encrypts the compressed snapshot using a separately stored Fernet key in `PB_BACKUP_ENCRYPTION_KEY`. Keep that backup key outside the repository and separate from `PLAY_RECEIPT_ENCRYPTION_KEY`. The latter is still needed to finalize any encrypted purchase tokens after restoration. Never put a backup, player keys, environment file or database connection string in the server repository.

With database credentials already set in the operator's environment, run `python backup_restore.py backup <private-path>/ledger-YYYYMMDD.pbbackup`; existing paths are never overwritten. `python backup_restore.py inspect <private-path>/ledger-YYYYMMDD.pbbackup` checks decryption and prints only schema/date/row counts. To prove restoration, point `PB_DATABASE_URL` at a separate **empty** test database and run `python backup_restore.py restore <private-path>/ledger-YYYYMMDD.pbbackup --confirm-empty-database`. It refuses a populated ledger, validates the approved table/column schema, and restores in one transaction. Verify a known recovery key, coin balance, ownership and purchase receipt before attesting durability or moving users. The local encrypted round-trip test covers these fields; a real Neon restore drill remains required.

Limits are one million rows, 128 MiB cleartext and 180 MiB encrypted file input. Beyond that size, use a separately tested provider/pg_dump backup procedure; this tool stops instead of silently creating a partial logical export. Backups are sensitive even when encrypted and need retention/access rules. No automatic schedule or cloud backup bucket is created by these commands.

`match_receipt` includes `match_id,status:"verified"|"rejected",winner` when verified, `coins`, `rating_delta`, `reason`, and current `profile`. `match_receipt_get {match_id}` recovers a committed settlement after reconnect; `replay_pending` means still pending. The independent Godot result determines the winner. Settlement is transactional and idempotent across retries/restarts. A process restart loses incomplete upload buffers, but never committed balances; incomplete matches remain unpaid and become rejected/expired after twenty minutes rather than pending forever. A peer who withholds their log can deny settlement: the UI must call that match unverified, not assign an invented win or loss. This remains a limitation of the direct-peer corroboration design.

Ranked completed match: 40 coins +20 winner. Public matchmade casual: 20 +10 winner. Coins never depend on damage, bricks or match length and defeat never removes coins. Rating starts 1000, ten placement matches, symmetric Elo K32 while either player is provisional then K24. Bronze below1200, Silver1200, Gold1400, Platinum1600, Diamond1800. After three rewarded matches against the same opponent in one hour, further meetings are practice with zero currency/rating. This blocks simple same-pair reward loops without a normal-play daily cap. These defaults are transparent playtest hypotheses, not measured retention claims.

## Release limits

Deterministic verification prevents invented scores, impossible physics and unilateral replay alteration when an honest peer corroborates inputs. It does not prove human input, prevent two-account collusion, or provide a live authoritative referee. Account creation remains device-key based and requires abuse monitoring before real-money launch. No matchmaking service can infer a fair disconnect winner solely from peer reports. Production launch still requires durable managed storage/backups, measured verifier capacity, matching client/server source versions, store and ad account configuration, service credentials, purchase refund/revocation handling, privacy/consent review and real-device Play sandbox tests. Do not label all of these configured merely because buttons exist.
