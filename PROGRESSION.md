# Progression extension v1

This extends `PONG_BREAKER_WEBRTC_1`. Direct WebRTC gameplay and the existing relay remain unchanged. Guest/private play continues when progression is unavailable. `round_complete` never credits currency or affects rating.

## Readiness and storage

`welcome` includes `progression_version:1` and `capabilities:{economy,ranked,match_rewards,ads,purchases,progression_version:1}`. A missing extension means an older server; do not send it credentials. Capability values are server configuration, never client switches.

Production: configure `PB_DATABASE_URL` to a PostgreSQL connection string with TLS (`sslmode=verify-full` preferred with the provider CA; at least `require`). Configure `PB_DURABLE_STORAGE=1` only after checking the database retention/backup policy. Install `requirements-progression.txt`. No database credentials belong in the Android build. No provider is provisioned by this code. A free database provider's quotas, suspension and retention rules must be checked before release.

Development SQLite: `PB_SQLITE_PATH` creates the schema but does not advertise the economy by default. `PB_SQLITE_PERSISTENT_VOLUME=1` explicitly attests an actual persistent volume and enables it; do not set this on ephemeral Render free storage. Render without this declaration refuses a SQLite launch. Existing `render.yaml` intentionally leaves the economy/ranked/purchase/ad gates closed. Losing a local database must never silently create an apparently restored account.

The database stores hashed, 256-bit bearer player keys. The original key is returned only once. Save it immediately and protect it. A key is a portable account recovery secret, not a public player name. There is no email/password account system or administrative recovery promise. Recovery & Privacy displays the private key and can replace it; possession of a valid key authorizes account access. Invalid saved keys fail without creating a replacement account. The server never logs keys, receipts or database URLs. Clients must scope saved keys to an approved TLS service origin and never send them to arbitrary custom servers.

## Account, shop and reward messages

Every request retains the existing unique `request_id` envelope. Mutation `operation_id` is a second stable retry key, 8–80 ASCII letters/digits/underscore/hyphen. Reuse it for retries of the SAME operation on a new request/connection. Changing its payload fails. Currency and ownership changes share one transaction. Rebuying an owned cosmetic never debits twice. Only the four Classic styles are owned and equipped at creation, alongside 150 welcome coins. Rally Pearl costs 200 coins, Rally Pro 300, and Prism Ceramic 350. Existing ownership is retained.

| Request | Fields | Response |
|---|---|---|
| `account_auth` | optional `token` (omit only for a new account) | `account` with `profile`, `catalog`, `capabilities`; `token` only for a newly created account |
| `account_delete` | `confirmation:"DELETE"`, `operation_id` | `account_deleted`; removes collection, wallet, key access and active sessions |
| `account_rotate` | `new_token` (43-character URL-safe encoding of 32 random bytes), `operation_id` | `account_rotated`; transactionally replaces the credential hash and revokes other sessions; idle only |
| `profile_get`, `reward_status` | none | `profile` with `profile`, `capabilities` |
| `catalog_get` | none | `catalog` with item array |
| `shop_buy` | `item_id`, `operation_id` | `purchase` with `result:{item_id,spent,already_owned}`, current `profile` |
| `cosmetic_equip` | `slot`, `item_id`, `operation_id` | `equipped` with `result`, current `profile`; refreshes lobby cosmetic display |
| `reward_prepare` | `operation_id` | `reward_prepared` with `custom_data`, `ssv_user_id`, `expires_at`, `coins` |
| `reward_claim` | `operation_id` | `reward_granted` with `result`, current `profile`; verified supporters only |
| `purchase_submit` | `product_id`, `purchase_token`, `operation_id` | `purchase` with `result`, current `profile` |

Profile shape: `account_id`, `billing_account_id` (SHA256 of account ID, for Google billing binding), integer `coins`, string array `owned`, `equipped:{ball,paddle,brick,theme}`, boolean `supporter`, `ranked:{rating,games,wins,provisional,placements_remaining,division}`, `reward:{coins:50,cooldown_seconds:14400,available_at,server_time}`, and `recent_receipts` (the latest ten completed/rejected settlements for reconnect recovery). Reward timestamps are Unix UTC seconds. Device clock changes cannot advance rewards. A new `reward_prepare` operation is required after its ten-minute challenge expires.

An idle, already authenticated connection may restore a different valid token; its previous profile is replaced only after token validation. Account deletion requires explicit DELETE confirmation while idle. It erases ownership, wallet, custom equipment, cooldown and local-operation history, makes the old key unusable, and clears other active sessions. Minimal pseudonymous purchase/ad transaction identifiers and match-fraud records remain to prevent replaying already consumed receipts. There is no name/email stored. These retention facts must be visible in the release privacy/deletion notice; deleting an account is not a store refund. Existing spent purchase tokens cannot be redeemed into a new account afterward.

IDs: `ball_1..8`, `paddle_1..8`, `brick_1..6`, `theme_conservatory`, `theme_observatory`, `theme_cloudline`, `theme_arcade`, `theme_rally`; classic IDs are `ball_classic`, `paddle_classic`, `brick_classic`, `theme_classic`. All five purchasable themes cost 1,200 coins. Rally Club preserves the pearl-and-navy presentation and original soundtrack; its equipment skins are separate purchases. Wide paddles are paired art, never a separate purchase. Cosmetic equip requests require ownership and correct slot. Shared cosmetic changes are held until the current match ends.

No network command grants coins or entitlements by itself. `purchase_submit` verifies the account-bound Google purchase, commits a durable idempotent entitlement, then consumes/acknowledges the product. If finalization fails, `result.finalized=false`; retry the SAME token so acknowledgement can finish without duplicating the grant. Only products `coins_500`, `coins_1500`, `supporter_coffee` exist. An SDK success callback is not a grant. AdMob calls `/rewards/admob?<original signed query>`; only a valid signed, account-bound, unexpired challenge callback can award the same 50 coins/4-hour cooldown. There is no forced ad. Supporters claim the identical reward without an ad and do not get a shorter cooldown. No reward is auto-collected while offline.

Paid purchases additionally require `PLAY_RECEIPT_ENCRYPTION_KEY` (a separately managed Fernet key) and a successful authenticated Voided Purchases reconciliation. Pending raw tokens are stored only as authenticated ciphertext until Google consumption/acknowledgement succeeds, then erased. Never commit this key or log a token. Keep the old encryption key available until its pending queue is cleared before rotating it. The worker runs at startup and every thirty minutes; failed finalization is retried from durable storage. The refund feed uses a 29-day overlap with idempotent token-hash revocation. A stored reconciliation checkpoint older than that window blocks new paid purchases pending operator review. This job cannot recover refunds Google no longer exposes after a long outage.

Refund policy: unspent paid coins are tracked separately behind the single displayed balance; cosmetic purchases spend those paid coins first. A verified refund removes only the remaining coins from that purchase, preserving earned coins and all already-owned cosmetics. If some refunded paid coins were spent, `profile.store_review=true` blocks further real-money purchases pending support review, while play, earned rewards, and the coin cosmetic shop remain usable. A verified supporter refund removes ad-skip entitlement. No negative balance, automatic cosmetic seizure, ranked ban or fabricated debt is imposed. This policy must be explained before purchase. Account deletion keeps the minimal token-hash ledger necessary to prevent replay and process later refunds.

## Matchmaking and independent replay

`quick_match` accepts `mode:"casual"|"ranked"` (default casual) and `game_protocol`. Queues never mix gameplay protocols or ranked/casual modes. Ranked requires `PONG_BREAKER_1_5`, an authenticated durable account and a matching verifier. Legacy guests remain eligible for guest casual play only. Initial skill window ±150 rating expands 75 per 15 seconds to ±600 and is rechecked while waiting. A player cannot match their own account. Invitation rooms and browsable lobbies have no rewards; eligible play begins through automatic public matchmaking. Repeat opponents and rematches have the same rewards as other verified matches.

`color_preference` accepts -1 (Either), 0 (Red), or 1 (Blue). Opposite explicit preferences are honored; otherwise a fresh unbiased draw chooses the host's color. `start.host_color` is presentation identity, separate from the physical host/guest role.

Room snapshots include `mode`, `matchmade` and server-owned cosmetics/rank. `start` includes server-generated `seed`, `match_id`, `mode`, `reward_eligible`, `host_color`, and `replay:{version:1,fps:60,max_frames:54000,chunk_frames:120,simulation_sha256}`. Eligible clients reject a different simulation hash before play. The release rules settle decisive goals chronologically, draw simultaneous final goals, and finish at 15 minutes by lives, then points, then draw.

Both clients upload the observed, applied input stream, never a winner claim. Frame order is set both aim values, `sim.step(1/60, targets)`, then release flagged balls. Each frame is `[x0,x1,aim0,aim1,release0,release1]`: x multiplied by 1000 (6000..354000), aim multiplied by 1000 (-1000..1000), release flags 0/1. Include the finishing frame and no later frames. The stock guest independently simulates the host's stream and validates its own recent input witnesses; host snapshots alone cannot author a different live state.

`replay_chunk {match_id,offset,frames}` accepts 1..120 frames. `replay_ack.offset` is the next expected frame. Normal clients send 48-frame chunks every 0.8 seconds and retain a bounded 1920-frame outbox. An exact already-recorded retry is acknowledged without double-appending; changed overlap or skipped offsets are rejected. Chunk rate is at most 10/second, inside the ordinary control-message limit. After reconnect, reauthenticate, obtain the pending receipt and resend unacknowledged chunks at their original offsets.

Canonical replay hashing uses compact ASCII JSON arrays, each followed by one LF. `replay_seal {match_id,sha256,frames}` seals one upload. `replay_pending` is not a grant. Matching complete evidence plus either valid seal can proceed to independent verification; withholding the second seal cannot veto a completed match. Conflicting streams become no contest.

`match_presence {match_id}` records authenticated service presence, and `match_concede {match_id}` records a voluntary departure. Ranked menus do not pause play. After 30 seconds of one-sided service absence, while the other participant has been present within 10 seconds, the service can adjudicate a forfeit. It must independently verify the two matching input prefixes first. Explicit concession uses the same evidence gate. If both remain present but input progress stalls for 30 seconds, neither can safely accuse the other: reject as interrupted. Both absent for over 35 seconds also become no contest. A finished verified prefix always uses its real result instead of a forfeit. No usable agreed prefix means no arbitrary rating loss.

An intact direct peer connection can continue through a brief lobby-service outage while reconnecting and catching up its records. A lost room is not recreated inside the completed match; the next game returns to matchmaking. A relay outage interrupts gameplay. A service restart loses incomplete in-memory uploads; returning participants receive a rejected `service_restarted` receipt instead of waiting indefinitely. Already committed receipts remain retrievable and duplicate submissions are idempotent.

The verifier executes only the trusted release simulation, never client code. Limits: two verification processes, a 45-second process timeout, 54000 frames/15 minutes, eight active eligible matches and 16-KiB messages. Completed games have no artificial 30-second minimum; the verifier must find a terminal result. Wall time must match replay duration within a five-second tolerance. Incomplete buffers expire after 20 minutes. Unavailable verification cannot invent rewards.

The engine is pinned to **Godot 4.7.2 stable**, checked at startup. `install_verifier.py` validates the official Linux archive's SHA512 before installation. `PB_GODOT_BINARY` points to that engine; `PB_REPLAY_SIMULATION` points to `verifier/simulation.gd`, copied byte-for-byte from the matching client. Resynchronize the hash and bump gameplay compatibility whenever rules change. Python dependencies and their tested transitive versions are pinned in `requirements-progression.txt`.

## No-cost staging setup, not a paid deployment

Use a Render Free Docker service with a **separate durable PostgreSQL database**, not Render's expiring free PostgreSQL trial. Render documents its free web filesystem as ephemeral and its free PostgreSQL database lifetime as thirty days: [Render free limits](https://render.com/docs/free). Neon is an eligible external free option; its [October 2, 2026 free-plan announcement](https://neon.com/blog/neon-free-plan-1-gb-per-project) lists 1 GB storage per project and 100 CU-hours monthly. These are quotas, not an unlimited-production promise or a backup substitute. On October 7, 2026, the owner approved the Neon Free database and new `pong-breaker-live` Docker service; both were deployed without a payment method. See [DEPLOYMENT.md](DEPLOYMENT.md) for the actual endpoint and verification evidence.

1. Create a Free Neon project in a region near the Render service, using a dedicated database role; leave paid upgrades and payment methods disabled. Save its TLS PostgreSQL connection string as a Render secret `PB_DATABASE_URL`, never in the app or repository.
2. Prepare and inspect the server-only repository with these files and the exact `verifier/simulation.gd`. The current Blueprint uses Docker so Linux runtime dependencies and the checksum-pinned engine are reproducible. Keep `plan: free`, automatic deployments off, and health path `/healthz`. An existing native-Python service may require an owner-approved new Docker service; do not silently replace the live endpoint.
3. Establish durable backup/export and restore procedures within free quotas. Only then set `PB_DURABLE_STORAGE=1`. Start with store/ad flags absent. Verify `welcome.capabilities.economy=true` and `ranked=true`, then run owned test clients. Never send actual user keys to a test endpoint.
4. Exercise the PostgreSQL adapter against an explicitly supplied staging URL: install `requirements-progression.txt`, set `PB_TEST_POSTGRES_URL`, and run `python run_tests.py`. It creates/removes only random `pong_test_*` schemas. This passed against the approved Neon PostgreSQL 18 database, including concurrent spending, reconnect persistence, verified refunds and encrypted restoration into a separate empty schema. The final suite passed 82 tests with no skips. Repeat the drill before a database migration or material schema change.
5. Keep paid purchases and rewarded ads disabled until Google Play/AdMob configuration, consent/audience review, encrypted finalization retries, refund reconciliation and real-device license-test purchases are verified. The code has no live account credentials and charges nobody.

Idle guest-only servers do not poll the database every minute: expired matches are revisited when players return, allowing serverless PostgreSQL to scale to zero. If commerce is enabled, its thirty-minute reconciliation wakes the database periodically and consumes some free compute allowance; include that in measured capacity. A wallet outage disables rewards and ranked starts, while a casual game can continue explicitly without rewards.

## Encrypted operator backup and restore drill

`backup_restore.py` provides a bounded logical export of every ledger table, with a repeatable read snapshot on PostgreSQL. It encrypts the compressed snapshot using a separately stored Fernet key in `PB_BACKUP_ENCRYPTION_KEY`. Keep that backup key outside the repository and separate from `PLAY_RECEIPT_ENCRYPTION_KEY`. The latter is still needed to finalize any encrypted purchase tokens after restoration. Never put a backup, player keys, environment file or database connection string in the server repository.

With database credentials already set in the operator's environment, run `python backup_restore.py backup <private-path>/ledger-YYYYMMDD.pbbackup`; existing paths are never overwritten. `python backup_restore.py inspect <private-path>/ledger-YYYYMMDD.pbbackup` checks decryption and prints only schema/date/row counts. To prove restoration, point `PB_DATABASE_URL` at a separate **empty** test database and run `python backup_restore.py restore <private-path>/ledger-YYYYMMDD.pbbackup --confirm-empty-database`. It refuses a populated ledger, validates the approved table/column schema, and restores in one transaction. Verify a known recovery key, coin balance, ownership and purchase receipt before attesting durability or moving users. The local encrypted round-trip and actual Neon restore tests cover these fields; all temporary PostgreSQL test schemas were removed afterward. This one-time verification does not replace ongoing protected backups and restore drills.

Limits are one million rows, 128 MiB cleartext and 180 MiB encrypted file input. Beyond that size, use a separately tested provider/pg_dump backup procedure; this tool stops instead of silently creating a partial logical export. Backups are sensitive even when encrypted and need retention/access rules. No automatic schedule or cloud backup bucket is created by these commands.

`match_receipt` includes `match_id`, `status:"verified"|"rejected"`, winner (-1 for draw) when verified, per-player `coins`, `rating_delta`, `reason`, and current `profile`. `match_receipt_get` retrieves a committed result or the pending state. Settlement is transactional and idempotent. The UI must reconcile its outcome with this receipt, including a receipt arriving before local gameplay ends.

Ranked completion: 40 coins +20 winner. Public casual: 20 +10. Draws pay completion only. Completed short games pay normally. Verified forfeits pay zero to the departing player; their winner gets only the completion amount after at least 600 agreed frames (10 seconds). Earlier forfeits pay neither player. Rating still follows a verified forfeit. There is no daily or repeated-opponent ordinary-match reward exclusion.

Rank starts at 1000; ten placement matches; symmetric Elo K32 while either player is provisional, then K24. A draw is a score of 0.5. Bronze below1200, Silver1200, Gold1400, Platinum1600, Diamond1800. Coin prices remain transparent playtest hypotheses, not measured retention claims.

## Public resources and operational limits

`/privacy` explains the current beta's data, retention and processors. `/account` accepts a private recovery code over the same secure WebSocket origin and offers deliberate typed account deletion. Codes never enter URLs, persistent browser storage or third-party scripts. The response allowlist applies CSP, no-store, nosniff, frame denial and no-referrer headers. Only the validated Render service hostname is automatically admitted as a browser origin; arbitrary cross-origin pages cannot use the account endpoint. Support/privacy contact: **PipeDreamInt@gmail.com**.

Account-key replacement preserves balances and ownership, invalidates the prior key and removes other live sessions. The client durably saves its proposed new key before sending the mutation, then probes that key after a lost reply; if it was not applied, it retries with the old key. Keep recovery codes private. Player names cannot recover an account.

Before restoring an old backup, reconcile deletions received after its timestamp against the separately protected operator record, and reapply them before reopening player access. The backup utility does not automate this reconciliation. Establish a named backup owner, daily protected snapshots, a documented retention limit and periodic isolated restore drills before accepting paid purchases. This package does not silently create a schedule or store an encryption key in source.

Replay verification rejects invented scores, impossible physics and unilateral stream alteration when an honest stock peer participates. It does not prove human input, prevent bots or two-account collusion, or provide a continuously authoritative server. Capacity is bounded; device-key creation still needs real operational abuse monitoring. Free hosting can sleep, restart or exhaust allowances. Do not promise unlimited production scale.

Paid purchases and ads remain disabled until provider accounts, consent/audience review and real-device transaction/refund testing are complete. Public release additionally needs final signing/application identity, policy/declarations and brand review, backup operations, capacity measurement, mobile accessibility and phone/network playtesting. Local fixture coverage is not store certification.
